# Office-Link 임원 질의 대비 주말 학습 가이드

이 문서는 최종 발표 자료 57장을 기준으로, 임원 질의에 단순 기능 설명이 아니라 **문제, 설계 선택, 동작 원리, 검증 결과, 한계**까지 답할 수 있도록 정리한 학습 자료다.

## 1. 가장 먼저 외울 핵심 메시지

### 한 문장 소개

Office-Link는 회의실, 방문객 주차, 식당, 사무용품, 사내 규정처럼 여러 시스템에 흩어진 사내 업무를 자연어 대화 하나로 조회하고, 중요한 변경 작업은 사용자가 구조화된 화면에서 최종 확인한 뒤 실행하는 AI 업무지원 서비스다.

### 30초 소개

기존에는 회의실 예약, 주차 등록, 비품 신청, 사내 규정 확인을 위해 서로 다른 시스템과 문서를 찾아야 했다. Office-Link는 AI Agent가 요청 의도를 분류하고 MCP Tool을 통해 필요한 정보를 조회한다. 예약이나 신청처럼 데이터를 변경하는 작업은 AI가 임의로 확정하지 않고 Action Draft를 만들어 사용자가 내용을 확인하고 수정한 뒤 승인한 값만 Backend가 실행한다. 사내 규정은 권한 기반 Hybrid RAG와 Re-ranker로 근거를 찾아 출처와 함께 답한다.

### 1분 소개

Office-Link의 핵심은 단순 챗봇이 아니라 **조회, 판단, 사용자 승인, 실행, 관측**을 하나의 흐름으로 연결했다는 점이다.

1. Planner가 대화 맥락과 현재 요청을 분석해 업무 도메인을 결정한다.
2. Action Agent가 허용된 Tool만 선택한다.
3. 조회는 MCP Server가 Workhub API와 RAG를 표준 Tool 계약으로 중계한다.
4. 생성, 수정, 취소는 공통 Action Draft로 구조화하고 사용자가 최종 승인한다.
5. 승인된 값은 Final Backend가 Workhub Backend에 직접 전달한다.
6. 실행 과정은 SSE로 보여주며 AOP와 Middleware 로그는 배치 수집해 Kafka와 관측 DB로 전달한다.
7. Agent 하네스, RAG 평가, 테스트 커버리지로 변경 이후 회귀와 모델 성능을 반복 검증한다.

### 임원에게 강조할 차별점 4개

- **안전성:** LLM이 변경 업무를 최종 확정하지 않는다.
- **확장성:** 업무 API를 MCP Tool 계약으로 연결하고 Agent에는 공통 Draft Tool을 둔다.
- **근거성:** 권한 필터, Hybrid Search, BGE Re-ranking, 위험 답변 검증을 거친다.
- **운영성:** 서버 간 인증, 재시도, 멱등성, 로그 파이프라인, 하네스와 커버리지를 포함한다.

## 2. 프로젝트 문제와 해결 방식

### 해결하려던 문제

- 업무마다 사용하는 화면과 절차가 다르다.
- 필요한 정보가 사내 시스템과 문서에 분산되어 있다.
- 사용자는 정확한 메뉴와 처리 절차를 매번 기억해야 한다.
- 자연어 Agent가 바로 변경 작업을 수행하면 잘못 해석한 값이 실제 업무에 반영될 위험이 있다.
- 사내 규정은 사용자 부서와 역할에 따라 공개 범위가 달라야 한다.

### 해결 원칙

- 사용자는 업무 시스템이 아니라 **업무 목적**을 말한다.
- AI는 필요한 조회와 실행값을 제안하되, 변경 작업의 최종 결정권은 사용자에게 둔다.
- 조회 결과는 긴 원본 JSON이 아니라 화면과 LLM에 필요한 Compact DTO로 제한한다.
- 규정 답변은 검색 근거와 출처를 포함하고, 권한 없는 문서는 검색 후보에 들어오지 않게 한다.
- 모델이나 코드가 바뀌어도 하네스로 기존 기능을 다시 검증한다.

## 3. 전체 시스템 구조

### 구성 요소와 책임

| 구성 요소 | 핵심 책임 | 왜 분리했는가 |
|---|---|---|
| Frontend | 채팅, SSE 렌더링, 표·카드·Draft Form, 사용자 상태 | 사용자 경험과 업무 실행 화면을 담당 |
| Final Backend | 로그인·권한, 채팅 저장, SSE 중계, Action Draft 실행, 로그 수집 | 사용자 접점과 신뢰 가능한 변경 실행 경계를 담당 |
| AI Agent | 의도 분석, 도메인 라우팅, Tool 선택, 응답 생성·검증 | LLM 오케스트레이션을 업무 API와 분리 |
| MCP Server | 조회 Tool 등록, 입력 검증, Workhub API 변환, Compact DTO, RAG 재정렬 | LLM Tool 계약과 업무 API 계약 사이를 중계 |
| Workhub Backend | 회의실·주차·식당·사무용품 업무 규칙, RAG 검색·저장 | 실제 업무 데이터와 규칙의 단일 책임자 |
| PostgreSQL | 사용자·채팅·로그 DB와 업무·RAG DB 분리 | 인증·관측과 업무 데이터의 경계를 유지 |
| Redis | Agent Checkpoint·장기 기억, 인증 상태, RAG 임베딩 캐시 | 빠른 상태 복원과 반복 계산 절감 |
| Kafka | 관측 로그 비동기 전달 | 업무 응답 경로와 로그 적재를 분리 |

### 대표 조회 흐름

```text
브라우저
→ Frontend
→ Final Backend
→ AI Agent
→ MCP Server
→ Workhub Backend
→ MCP Compact DTO
→ AI 최종 답변
→ SSE
→ 사용자 화면
```

### 대표 변경 흐름

```text
사용자 자연어 요청
→ AI가 Action Draft 생성
→ Frontend가 빠른 실행 카드 또는 수정 Form 표시
→ 사용자가 최종값 확인·수정·승인
→ Final Backend가 승인된 payload만 검증
→ Workhub Backend 업무 API 실행
→ 실행 결과를 카드와 목록에 반영
```

### 왜 조회와 변경 경로가 다른가

조회는 잘못 선택해도 데이터를 바꾸지 않으므로 Agent와 MCP가 자동으로 수행할 수 있다. 반면 생성, 수정, 취소는 실제 상태를 바꾸므로 AI의 추론 결과를 곧바로 실행하지 않는다. 사용자가 확인한 payload를 Final Backend가 실행하도록 분리해 Human-in-the-loop를 보장했다.

## 4. AI Agent 구조

### Planner와 Action을 나눈 이유

- Planner는 **무슨 업무인가**를 판단한다.
- Action은 **어떤 Tool을 어떤 인자로 실행할 것인가**를 판단한다.
- 역할을 분리하면 도메인 오분류와 Tool 오호출을 각각 추적하고 평가할 수 있다.
- 도메인별 허용 Tool을 제한해 불필요한 Tool 탐색 범위를 줄인다.

### 8개 라우팅 결과

| 라우팅 값 | 처리 |
|---|---|
| `meeting_room` | 회의실 조회·예약 Draft |
| `parking` | 주차 현황·방문객 등록 Draft |
| `supply` | 사무용품 조회·신청 Draft |
| `cafeteria` | 메뉴·운영시간·혼잡도 조회 |
| `childcare` | 어린이집 관련 규정 검색 경로 |
| `policy_rag` | 공통 사내 규정 RAG |
| `smalltalk` | 업무 Tool 없이 일반 대화·기억 처리 |
| `unknown` | 판단이 어렵거나 지원 범위 밖인 요청의 안전한 폴백 |

`childcare`가 별도 라우팅 값이어도 전용 MCP Tool이 있는 것은 아니다. 어린이집 문서는 사내 규정 검색 Tool을 재사용한다. 따라서 **라우팅 도메인 개수와 MCP 업무 도메인 개수는 같은 개념이 아니다.**

### 멀티턴 판단 원칙

- 최근 발화에 명시 대상이 있으면 최근 발화를 우선한다.
- “그거”, “1번”처럼 단독으로 의미가 없을 때만 이전 맥락을 참조한다.
- 도메인과 의도 요약만 Planner가 만들고 Tool과 인자 추출은 Action이 담당한다.
- 단기 기억은 Redis Checkpoint, 장기 기억은 Redis Store에서 주입한다.

### Tool 구성

- MCP Tool 13개
- Agent 공통 Tool 3개
  - `prepare_action_draft`
  - `save_memory`
  - `delete_memory`

Agent 내부 Tool은 외부 업무 API가 아니라 오케스트레이션 상태를 다루는 기능이다. 특히 도메인별 Draft Tool을 하나씩 두지 않고 `action_type`으로 구분하는 공통 Draft Tool을 사용해 Agent 확장 범위를 줄였다.

## 5. MCP Server를 도입한 이유

### 핵심 답변

MCP는 단순 HTTP 프록시가 아니라 **LLM이 이해하는 Tool 계약과 기존 업무 API 계약 사이의 어댑터이자 통제 지점**이다.

### MCP가 수행하는 일

- Agent에 노출할 Tool만 등록한다.
- Pydantic Schema로 입력 형식과 필수값을 검증한다.
- 날짜, 시간, 별칭 등을 업무 API 형식으로 변환한다.
- 사용자 ID, 부서, 역할과 서비스 토큰을 다음 서버로 전달한다.
- Workhub 원본 응답에서 불필요한 필드를 제거해 Compact DTO로 만든다.
- RAG 후보를 BGE Re-ranker로 재정렬한다.
- Tool 호출과 외부 API 결과를 표준 로그로 남긴다.

### 왜 Agent가 Workhub를 직접 호출하지 않는가

- Backend API가 바뀌어도 Agent의 Tool 계약을 안정적으로 유지할 수 있다.
- LLM에 지나치게 상세한 내부 DTO와 API 구조를 노출하지 않는다.
- Tool 노출 범위, 입력 검증, 응답 표준화를 한 곳에서 통제할 수 있다.
- 새로운 업무를 동일한 Tool 등록 규칙으로 확장할 수 있다.

### 왜 변경 Tool은 MCP에 노출하지 않았는가

회의실 예약, 방문객 주차 등록, 사무용품 신청의 생성·수정·취소 Tool은 존재하더라도 Agent에 등록하지 않는다. 변경 업무는 Action Draft에서 사용자 승인을 받은 뒤 Final Backend가 직접 Workhub API를 호출한다. 이는 MCP를 포기한 것이 아니라 **조회 자동화와 상태 변경 승인을 서로 다른 위험 수준으로 설계한 것**이다.

### Compact DTO의 효과

- LLM 입력 토큰 감소
- 원본 응답의 내부 필드 노출 감소
- 화면 렌더링 형식 통일
- LLM이 해석해야 하는 선택지 감소
- Tool 응답 계약 테스트 용이

## 6. Action Draft와 빠른 실행

### 기존 대화형 승인의 한계

- 최종값 일부를 바꾸려면 다시 대화해야 했다.
- 확인 대화와 Tool 호출이 추가되어 토큰과 지연이 늘었다.
- 사용자가 변경될 값을 한 화면에서 비교하기 어려웠다.
- 작은 모델은 확인 대화의 다양한 표현까지 학습해야 했다.

### 개선 구조

1. 자연어에서 날짜, 시간, 인원, 차량 번호, 품목과 수량을 추출한다.
2. 누락된 값에 업무 기본값을 적용한다.
3. 조건에 맞는 실행 가능 값을 제안한다.
4. 구조화된 Action Draft를 저장한다.
5. 필수값이 모두 있으면 빠른 실행 카드를 보여준다.
6. 부족하거나 사용자가 수정하려 하면 Form을 보여준다.
7. 사용자가 확인한 최종값만 실행한다.

### 기본값과 자동 추천

- 회의실: 현재 날짜·시간, 기본 사용 시간, 인원 조건을 만족하는 가장 작은 정원 회의실
- 주차: 방문 날짜와 잔여 비율을 고려한 주차장 추천, 차량 번호가 없으면 빠른 실행 제외
- 사무용품: 언급한 품목별 기본 수량 1개, 재고 내 수량 제안

자동 대체는 **사용자에게 보여줄 제안값 생성 단계에서만** 수행한다. 사용자가 확인한 후 실제 실행 과정에서 충돌이 생기면 임의로 다른 회의실이나 품목으로 바꾸지 않고 실패 사유를 안내한다.

### 안전장치

- Draft 상태와 만료 시간 관리
- 실행 중 중복 클릭 방지
- 승인 payload와 저장된 Draft의 일치 여부 검증
- 재고, 회의실 충돌, 운영시간을 Workhub가 실행 직전에 재검증
- 성공 후 수정 버튼 비활성화 및 목록 스냅샷 갱신
- 멱등 키로 중복 변경 방지

## 7. 업무 도메인별 설명

### 회의실

- 조건별 회의실 목록, 상세 정보, 내 예약 목록 조회
- 날짜·시간·인원·장비 조건 필터
- 예약 생성·시간 변경·취소는 Draft 승인 경로
- 동시 예약 충돌과 운영시간을 Workhub에서 최종 검증
- 예약 목록은 다가오는 예약부터 표시

### 방문객 주차

- 주차장 현황과 내 등록 목록 조회
- 차량 번호, 방문일, 담당자 또는 방문객, 주차장으로 Draft 생성
- 오늘 요청은 잔여 비율이 높은 주차장을 추천하고 미래 요청은 지정 기본값을 사용
- 추천은 강제 제한이 아니며 최종 업무 규칙은 Backend가 판단

### 식당

- 운영시간, 날짜별 메뉴, 주간 메뉴, 실시간 혼잡도 조회
- 여러 식당과 여러 끼니를 한 번의 사용자 목적 단위 Tool로 반환
- 스케줄러가 데모용 혼잡도 데이터를 갱신

### 사무용품

- 신청 가능 품목과 재고, 내 신청 상태 조회
- 최대 5개 품목을 하나의 Draft에 구성
- 중복 품목 선택 방지와 품목별 재고 검증
- 수정 시에도 현재 재고와 기존 신청량을 고려해 검증

### 사내 규정

- 사용자 권한을 반영한 문서 검색
- 일반 질문은 `policy_search_document`
- 출처 문서나 원문 요청은 `policy_get_source`
- 답변에 문서명과 섹션 출처 포함

## 8. RAG 구조

### 전체 흐름

```text
사용자 질문과 인증 맥락
→ 권한 Hard Filter
→ 질문 임베딩
→ Vector + Keyword Hybrid Search
→ 후보 10개
→ BGE v2-m3 Re-ranking
→ 최종 근거 5개
→ 근거 기반 초안과 출처
→ 코드 검증
→ 위험한 경우에만 LLM 의미 검증·1회 교정
→ 최종 답변
```

### 임베딩 대상

본문만 임베딩하지 않고 다음을 함께 임베딩한다.

```text
문서명 + 섹션명 + 본문
```

이렇게 하면 사용자가 문서명이나 규정의 장 제목으로 질문해도 의미 검색에서 찾기 쉬워진다.

### 메타데이터 역할

- 검색·출처: 문서 ID, 청크 ID, 제목, 버전, 도메인, 카테고리
- 접근 제어: 공개 범위, 허용 부서, 허용 역할
- 품질·운영: 문서 상태, 버전, 임베딩 모델과 갱신 상태

### Hard Filter와 Soft Boost

- 부서와 역할은 보안이므로 Hard Filter다. 권한 없는 문서는 후보에 포함하지 않는다.
- 도메인과 카테고리는 검색 힌트이므로 Soft Boost다. Planner가 도메인을 잘못 추론해도 관련 문서가 완전히 제외되지 않게 했다.

### 최종 검색 설정

| 항목 | 설정 |
|---|---|
| 검색 | Hybrid Search |
| 가중치 | Vector 0.6 : Keyword 0.4 |
| 임계값 | Vector 0.45, Keyword 0.20 |
| 1차 후보 | 10개 |
| 최종 근거 | 5개 |
| Re-ranker | `BAAI/bge-reranker-v2-m3` |
| 실행 엔진 | OpenVINO FP32 |
| 입력 길이 | 최대 256 tokens |

### 왜 Hybrid Search인가

- Vector 검색은 표현이 달라도 의미가 비슷한 질문에 강하다.
- Keyword 검색은 문서명, 규정명, 고유명사와 정확한 용어에 강하다.
- 사내 규정은 자연어 질문과 문서 고유 용어가 함께 나오므로 둘을 조합했다.

### 왜 Re-ranker가 필요한가

1차 Retriever는 넓게 후보를 찾는다. Cross Encoder 기반 BGE Re-ranker는 질문과 각 후보를 함께 읽어 정답 근거를 상위로 올린다. 약간의 지연이 증가하지만 상위 근거가 최종 답변 품질을 좌우하는 RAG 특성을 고려해 정확도를 우선했다.

### 검색 성능 실험

300개 평가 질문에 정답 문서·청크, 무응답 여부, 사용자 권한을 라벨링했다. 개발용 50개로 설정을 선택하고 별도의 최종 평가용 250개로 일반화 성능을 검증했다.

- Vector Only, Keyword Only, Hybrid 비율과 임계값 비교
- Hybrid 6:4, Vector 0.45, Keyword 0.20 선택
- 낮은 임계값 조합의 무응답 오류율 41.51%를 9.43%로 감소
- BGE Re-ranker 적용 시 MRR@5 86.33%에서 92.50%로 향상
- OpenVINO FP32로 PyTorch FP32 대비 P95 2,598ms에서 1,137ms로 56.2% 단축
- 250건에서 Top-1 결과 차이 0으로 검색 품질 유지

### 위험 답변만 검증하는 이유

모든 답변을 다시 LLM으로 검증하면 비용과 지연이 거의 한 번 더 발생한다. 먼저 코드가 인용 청크 존재, 문서명 일치, 빈 검색 결과 단정 여부, 출처 누락을 검사한다. 검색 결과 없음, 낮은 점수, 작은 점수 차이, 근거 불일치 같은 위험 신호가 있을 때만 LLM이 원문 청크와 답변 주장 사이의 의미 일치를 검증한다.

### Self-Correction은 무엇을 고치는가

문장을 단순히 다듬는 기능이 아니다. 원본 청크를 다시 제공하고 다음을 한 번만 교정한다.

- 근거에 없는 주장 제거
- 과도한 단정 완화
- 잘못되거나 누락된 출처 수정
- 검색 근거와 의미가 맞도록 답변 재구성

## 9. 인증과 보안

### 사용자 인증과 서버 인증을 나눈 이유

- 사용자 로그인은 Azure SSO와 사용자 JWT로 처리한다.
- 서버 간 호출은 사용자의 세션을 재사용하지 않고 OAuth2 Client Credentials로 별도 서비스 토큰을 발급한다.
- 호출 주체별 최소 Scope를 부여해 한 서버의 토큰이 모든 API를 호출하지 못하게 한다.

### 서버 호출 Scope

```text
Final Backend → AI Agent: ai-agent.invoke
AI Agent → MCP Server: mcp.call
MCP Server → Workhub Backend: workhub.api
Final Backend → Workhub Backend: workhub.api
```

### 검증 항목

- JWT 서명
- 발급자 `issuer`
- 대상 `audience`
- 만료 시간
- 호출 주체
- 필요한 Scope

공개키는 JWKS로 제공해 대상 서버가 검증한다. 비밀키와 API Key는 `.env`로 외부화하고 Git에 커밋하지 않는다.

### 임원 질문에서 솔직히 말해야 할 외부 의존성

Plan·Action 모델은 온프레미스 LLM을 사용하지만 음성 인식과 임베딩은 OpenAI API를 사용한다. 따라서 현재 구조가 완전한 폐쇄망 온프레미스라고 말하면 안 된다. 민감도 높은 운영 환경에서는 로컬 음성·임베딩 모델로 교체하거나 전송 데이터를 최소화하는 추가 정책이 필요하다.

## 10. Retry와 멱등성

### Retry가 필요한 이유

MSA에서는 사용자 요청 하나가 여러 서버 호출로 이어진다. 중간의 일시적인 네트워크 장애 하나가 전체 요청 실패가 되면 서비스 품질이 크게 떨어진다. 따라서 복구 가능한 오류만 선별해 재시도한다.

### 재시도 대상

- `429`: 일시적인 요청 제한
- `502`, `503`, `504`: 게이트웨이 또는 일시적 서버 장애
- 네트워크 연결 실패와 제한 시간 초과 중 복구 가능한 경우

### 재시도하지 않는 오류

- `400`: 입력 오류
- `401`, `403`: 인증·권한 오류
- `409`: 업무 충돌 또는 멱등 키 충돌
- `422`: 검증 오류

이 오류는 기다린다고 해결되지 않으므로 원인별 사용자 메시지로 처리한다.

### Exponential Backoff + Jitter

재시도 간격을 지수적으로 늘리고 작은 무작위 지연을 추가한다. 여러 요청이 동시에 실패한 뒤 같은 시점에 재시도해 서버를 다시 압박하는 동시 재시도 문제를 줄인다.

### 멱등성이 필요한 이유

변경 요청을 재시도하면 같은 예약이나 신청이 두 번 생성될 수 있다. 멱등 키와 payload hash를 저장해 같은 요청은 최초 결과를 재사용한다.

| 상황 | 처리 |
|---|---|
| 처음 요청 | 업무 실행 후 결과 저장 |
| 같은 키·같은 payload, 완료 | 저장된 결과 반환 |
| 같은 키·같은 payload, 처리 중 | 202와 재시도 시점 안내 |
| 같은 키·다른 payload | 409 충돌 응답 |

MCP 내부에서는 상위 요청 키에 Tool 이름과 입력 식별값을 결합해 같은 상위 요청에서 동일 Tool을 다시 호출하는 경우도 구분한다.

## 11. 로그와 관측

### 로그 파이프라인

```text
AOP / Middleware / Decorator
→ 서비스 메모리 배치
→ Final Backend 로그 Batch API
→ Kafka
→ Consumer
→ 관측 로그 테이블
→ 관리자 대시보드
```

### 왜 메모리 배치와 Kafka를 쓰는가

- 매 이벤트마다 DB에 직접 쓰면 사용자 응답 지연이 커진다.
- 로그 적재 장애가 업무 요청을 실패시키면 안 된다.
- Batch API와 Kafka가 서비스 실행과 로그 저장의 결합도를 낮춘다.
- Consumer가 재처리와 적재 속도 조절을 담당할 수 있다.

### 주요 로그

- 인증·로그인 감사 로그
- 공통 관측 이벤트
- Tool 호출 입력·결과·지연
- LLM 모델·토큰·지연
- RAG 검색 후보·문서·점수·지연
- Action Draft 생성·승인·완료·실패 생명주기

### 업무 거절과 시스템 실패

예약 충돌, 운영시간 위반, 재고 부족은 시스템이 정상적으로 업무 규칙을 적용한 `rejected`다. DB 장애, 연결 실패, 예상하지 못한 예외는 `failure`다. 이를 분리해야 관리자 대시보드의 답변 실패율이 업무상 정상 거절 때문에 왜곡되지 않는다.

### Dashboard 지표

- 답변 지연시간
- 요청 수와 답변 성공률
- 총 토큰 사용량
- 가장 많이 사용된 도메인
- 도메인별 요청당 평균 토큰
- 도메인별 Tool 호출 횟수
- RAG 검색 현황과 노출 문서 Top 5
- 로그인 사용자 추이와 최근 인증 로그

## 12. Redis와 멀티턴

### 단기 기억

LangGraph Checkpoint에 대화 상태와 최근 메시지를 저장한다. 같은 대화방 요청에서 이전 대화와 Tool 결과를 복원한다. Checkpoint TTL로 영구 누적을 방지한다.

### 대화 요약

대화가 일정 길이를 넘으면 오래된 메시지를 요약해 남기고 원문 일부를 제거한다. 이후에는 요약과 최근 발화를 함께 사용해 컨텍스트 길이를 제한한다.

### 장기 기억

사용자가 “기억해 줘”라고 명시한 사실, 지속 표현이 있는 선호, 재사용 가능성이 높은 정보만 저장한다. 같은 key는 최신 값으로 갱신하고 저장 후보 수를 제한한다.

### 기억의 위험과 대응

- 잘못 저장된 기억: 사용자가 삭제하거나 수정 가능
- 개인정보 과다 저장: 명시 요청과 재사용성 기준으로 제한
- 오래된 선호: 최신 값으로 덮어쓰기, 향후 만료·신뢰도 정책 필요

## 13. 온프레미스 LLM 선정

### 도입 이유

- 전사 사용 시 API 토큰 비용 증가 가능성
- 외부 API 의존성과 민감 데이터 전송 부담
- 사내 GPU 자원 활용

### 후보 선정 조건

- RTX 3090 24GB 환경에서 구동 가능
- Tool Calling 가능
- Reasoning과 한국어 요청 처리 가능
- 초당 80 tokens 이상을 초기 목표로 검토

### 8B Fine-tuning에서 확인한 문제

- Training loss가 매우 빠르게 낮아져 과적합 징후가 나타났다.
- 같은 의미라도 표현이 달라지면 Tool 호출 형식을 안정적으로 만들지 못했다.
- 새 도메인이나 Tool이 추가될 때마다 재학습이 필요해 확장성이 떨어졌다.

따라서 모델 규모와 구조화 출력 안정성을 다시 비교하고, 공통 Draft Tool과 Tool Schema를 단순화해 모델이 학습해야 할 표면을 줄였다.

### 최종 모델 비교 결과

| 지표 | Gemma 26B Q4 | GPT-5 | GPT-5 mini |
|---|---:|---:|---:|
| 전체 통과율 | 97.26% | 94.52% | 94.52% |
| 통과 케이스 | 71/73 | 69/73 | 69/73 |
| 평균 E2E | 15.91초 | 20.66초 | 7.28초 |
| 평균 TTFT | 15.47초 | 20.27초 | 6.83초 |
| 평균 Tool 지연 | 0.29초 | 0.34초 | 0.30초 |
| 평균 토큰 | 9,691 | 9,383 | 9,453 |

### 왜 Gemma 26B Q4를 선택했는가

최저 지연만 보면 GPT-5 mini가 유리하다. 그러나 동일한 73개 업무 테스트에서 Gemma가 더 높은 최종 통과율을 보였고, 외부 API 호출 비용 없이 사내 GPU에서 운영할 수 있다는 점을 함께 고려했다. 즉 **일반 지능이 더 우수하다고 주장한 것이 아니라, 우리 Tool 계약과 업무 데이터셋에서 더 높은 통과율을 보인 운영 후보**로 선택한 것이다.

### Q4 양자화의 의미

가중치를 4비트 수준으로 줄여 VRAM 사용량을 낮춘다. 정확도 저하 가능성이 있으므로 단순히 메모리 절감만 보고 적용하지 않고 동일 하네스 데이터셋으로 Tool 정확도와 응답 형식을 다시 검증했다.

### 비용 설명 시 주의

온프레미스 모델은 API 토큰 과금이 없을 뿐 무료가 아니다. GPU 구매·감가상각, 전력, 운영 인력, 장애 대응 비용이 있다. 발표에서는 “API 종량 비용과 외부 의존성을 줄였다”고 표현한다.

## 14. 테스트 하네스

### 왜 일반 단위 테스트만으로 부족한가

LLM은 같은 코드에서도 모델, 프롬프트, 표현에 따라 다른 Tool과 인자를 만들 수 있다. 따라서 실제 인증부터 SSE 종료까지 운영 흐름을 재현하는 별도 Agent 평가가 필요하다.

### 데이터셋

- 개발용 73개: 개발 중 반복 실행하고 실패 원인을 분석해 개선
- 최종 평가용 60개 Holdout: 설정 선택에 사용하지 않고 최종 모델 비교에만 사용
- 질문별 기대 도메인, Tool, 호출 순서, 필수 인자, 화면 출력, 정상 종료 조건 정의
- RAG 문항은 정답 문서·청크·무응답 여부·권한을 별도 평가

### 실행과 수집

- 실제 OAuth2 서버 인증 사용
- 실제 사용자 권한과 기준 시각 적용
- SSE 시작부터 종료까지 수집
- Domain, Tool, 호출 순서, 인자, 구조화 출력, 최종 답변, 오류 수집
- `request_id`와 `trace_id`로 SSE 결과와 AOP 로그 연결
- 첫 토큰 시간, 전체 완료 시간, Tool 지연, 입력·출력 토큰 측정

### 자동 채점

- 도메인 정확도
- 필수 Tool Recall
- Tool 호출 순서
- 필수 인자 정확도
- 구조화 출력 조건
- 정상 완료 여부

### LLM-as-a-Judge

생성형·RAG 답변만 평가하고 고정 UI 문구는 제외한다.

- 사실 정확성 30%
- 질문 의도 충족 25%
- 검색·Tool 근거 일치 25%
- 논리 일관성·명확성 20%

기능 통과율, 답변 품질 통과율, 둘을 모두 만족한 최종 통과율을 분리해 보고한다.

### 지속적 개선 흐름

```text
기능 추가·코드 수정·모델 교체
→ 개발용 문항 실행
→ 자동 채점과 실패 분석
→ 코드·프롬프트·Tool 개선
→ 재실행해 회귀 여부 확인
→ 최종 평가용 Holdout으로 비교
```

## 15. 테스트 커버리지

Frontend를 제외한 네 서버의 핵심 업무 경로를 자동화했다.

- Java Backend 2개: JUnit + JaCoCo
- AI Agent와 MCP Server: pytest + pytest-cov
- 통합 라인 커버리지: 73.63%

커버리지는 품질 그 자체가 아니라 어떤 코드가 테스트되지 않았는지 찾는 지표다. 핵심 업무 규칙, Draft 상태 전이, 인증, 멱등성, Tool 계약, RAG 필터를 우선 테스트하고 단순 DTO나 프레임워크 설정을 숫자 채우기 목적으로 테스트하지 않았다고 설명한다.

## 16. 데이터와 저장 구조

### DB를 분리한 이유

- Final Backend DB: 사용자, 권한, 채팅, Action Draft, 로그
- Workhub DB: 회의실, 주차, 식당, 사무용품, RAG 문서·청크·권한

업무 데이터와 인증·관측 데이터를 분리해 서비스 책임과 장애 범위를 명확히 했다. 발표 자료 기준 총 42개 테이블과 397개 컬럼이다.

### Snapshot의 역할

채팅 메시지는 텍스트만 저장하면 표와 카드 UI를 새로고침 후 복원할 수 없다. 공통 도메인 Snapshot에 당시의 구조화 결과를 저장해 다시 접속했을 때 목록·상세·완료 카드를 복원하고, 수정·취소 이후 변경된 상태를 반영한다.

## 17. 확장 방식

### 새로운 조회 도메인 추가

1. Workhub에 업무 API와 규칙을 구현한다.
2. MCP에 입력 Schema와 Compact DTO Tool을 등록한다.
3. Agent 도메인 허용 Tool과 프롬프트 예시를 추가한다.
4. Frontend에 표·카드 Renderer가 필요하면 추가한다.
5. 하네스 개발용 문항과 권한·오류 테스트를 추가한다.

### 새로운 변경 도메인 추가

1. Workhub 생성·수정·취소 API 구현
2. 공통 `prepare_action_draft`의 `action_type` 계약 추가
3. Final Backend 승인·실행 Handler 추가
4. Frontend의 actionType별 Form Renderer 추가
5. 멱등성, 만료, 동시 실행, 실패 문구 테스트 추가

모든 코드가 무수정으로 확장된다고 말하면 안 된다. 다만 공통 Agent Tool, 공통 Draft Container, 표준 MCP 계약 덕분에 새 도메인마다 Agent Tool을 새로 설계하는 범위는 줄었다.

## 18. 한계와 향후 발전

### 현재 한계

- Planner는 한 요청에서 핵심 도메인 하나를 선택하므로 복합 업무를 완전히 분해하지 못한다.
- Agent 처리 시간의 대부분은 Tool이 아니라 LLM 첫 토큰 대기다.
- 온프레미스 Plan·Action 외에 음성 인식과 임베딩은 외부 API 의존성이 남아 있다.
- RAG 평가 300개는 사내 문서 전체 표현을 대표하기에 제한적일 수 있다.
- LLM Judge는 평가 모델의 편향이 있어 결정적 채점과 함께 사용해야 한다.
- 단일 Docker Compose 환경은 교육·시연에는 적합하지만 고가용성 운영 구조는 아니다.
- 장기 기억의 만료, 사용자별 민감도, 신뢰도 정책은 더 고도화할 수 있다.

### 발표 자료의 향후 계획

- 한 요청의 여러 업무를 분리·순차 실행하는 복합 업무 처리
- 중복·오래된 기억 정리와 맞춤 추천을 포함한 장기 기억 고도화
- 업무 마감과 예정 일정 알림
- 사용자 피드백 기반 재답변과 품질 개선
- 대화 제목 검색, 즐겨찾기, 기존 요청 재사용

## 19. 임원 예상 질문과 권장 답변

### 1. 이것이 일반 ChatGPT와 무엇이 다른가요?

일반 대화 모델은 답변 생성에 중심이 있지만 Office-Link는 인증된 사용자 맥락으로 실제 사내 데이터를 조회하고, 변경 업무는 사용자가 확인한 값만 실행하며, 전 과정을 로그와 테스트로 검증하는 업무 시스템이다.

### 2. 왜 화면을 하나 더 만들었나요? 기존 시스템 링크만 연결하면 되지 않나요?

링크 모음은 사용자가 여전히 각 시스템의 절차를 알아야 한다. Office-Link는 사용자의 목적을 입력으로 받아 필요한 조회, 추천, 값 구조화까지 수행하고 최종 확인만 사용자에게 남긴다.

### 3. AI가 잘못 예약하면 어떻게 하나요?

AI는 예약값을 제안할 뿐 확정하지 않는다. 사용자가 Draft에서 확인한 값만 Backend가 실행하고, 실행 직전에 Workhub가 충돌과 업무 규칙을 다시 검증한다.

### 4. 이미 확인한 뒤 다른 사람이 먼저 예약하면요?

Draft 시점의 가능 여부는 제안일 뿐이다. 승인 시점에 Workhub가 트랜잭션과 충돌 검사를 다시 수행하고, 충돌이면 다른 회의실로 임의 변경하지 않고 사용자에게 안내한다.

### 5. MCP가 없으면 구현할 수 없나요?

직접 API 호출로도 구현은 가능하다. MCP를 사용한 이유는 Tool 노출, 입력 Schema, 사용자 맥락 전달, 응답 표준화와 API 변환을 하나의 계약으로 관리해 Agent와 업무 서버의 결합도를 낮추기 위해서다.

### 6. 변경 작업이 MCP를 우회하면 MCP 확장성 취지와 어긋나지 않나요?

조회 자동화와 상태 변경은 위험 수준이 다르다. 조회는 MCP를 통해 자동화하고, 변경은 공통 Draft와 사용자 승인 경계를 거쳐 Backend가 실행한다. 확장성을 유지하면서도 LLM이 실제 변경을 확정하지 못하게 한 의도적인 분리다.

### 7. 새로운 업무를 추가하려면 얼마나 수정해야 하나요?

업무 API와 MCP 조회 Tool, 필요 시 화면 Renderer는 추가해야 한다. 다만 Agent에는 도메인별 변경 Tool 대신 공통 Draft Tool을 사용하므로 매번 Tool 선택 구조 전체를 늘리지 않는다. 하네스 문항을 함께 추가해 기존 기능 회귀도 확인한다.

### 8. 권한 없는 문서가 LLM에 전달될 가능성은 없나요?

부서와 역할 권한은 답변 생성 후가 아니라 검색 전에 Hard Filter로 적용한다. 따라서 권한 없는 문서는 후보 청크와 LLM 컨텍스트에 들어가지 않는다.

### 9. Planner가 도메인을 잘못 고르면 관련 문서를 못 찾지 않나요?

접근 권한만 Hard Filter이고 도메인과 카테고리는 Soft Boost로 적용한다. 도메인 추론이 틀려도 관련 문서가 완전히 제거되지 않게 설계했다.

### 10. 왜 Vector 검색만 쓰지 않았나요?

의미가 다른 표현에는 Vector가 강하지만 문서명과 사내 고유 용어에는 Keyword가 강하다. 두 특성이 공존하는 사내 규정 특성 때문에 Hybrid를 선택했고 평가 데이터로 비율과 임계값을 정했다.

### 11. Re-ranker 때문에 느려지지 않나요?

지연은 추가되지만 정답 근거가 상위에 배치되는 비율이 개선됐다. 이후 같은 BGE 모델을 OpenVINO FP32로 실행해 검색 품질을 유지하면서 P95를 56.2% 단축했다.

### 12. 왜 모든 RAG 답변을 다시 검증하지 않나요?

모든 답변을 LLM으로 재검증하면 비용과 지연이 이중으로 발생한다. 코드 검증으로 명확한 오류를 먼저 찾고, 낮은 점수나 근거 불일치 같은 위험 신호가 있을 때만 원문을 보며 검증한다.

### 13. 검색 결과가 없으면 어떻게 하나요?

규정을 추측해 답하지 않고 현재 권한으로 관련 문서를 찾지 못했다는 폴백을 반환한다. 무응답 질문의 잘못된 문서 반환률을 검색 설정 선택 기준에 포함했다.

### 14. 온프레미스 모델이 GPT보다 좋은 모델이라는 뜻인가요?

일반 능력 전체가 더 좋다는 뜻은 아니다. 우리 73개 Tool 계약 평가에서 더 높은 통과율을 보였고, API 비용과 외부 의존성까지 고려해 운영 후보로 선정했다.

### 15. 온프레미스는 정말 비용이 없나요?

토큰 종량 과금은 없지만 GPU, 전력, 운영 비용이 있다. 사용량이 커질수록 API 비용과 비교해 유리할 가능성이 있으며 실제 운영량을 기준으로 TCO를 계산해야 한다.

### 16. GPT-5 mini가 더 빠른데 왜 선택하지 않았나요?

지연만 보면 GPT-5 mini가 유리하다. 다만 핵심 업무에서는 정확한 Tool과 인자가 우선이고, Gemma가 평가 통과율이 더 높았다. 응답 지연은 향후 모델 서빙 최적화와 Planner 경량화 대상으로 남겼다.

### 17. Fine-tuning은 성공했나요?

8B 모델 Fine-tuning 실험에서는 과적합과 표현 변화에 대한 구조화 호출 불안정을 확인했다. 이 결과로 단순 데이터 확대보다 Tool 수와 Schema를 줄이고 더 큰 양자화 모델을 비교하는 방향으로 전환했다. 실험 실패도 최종 구조 선택의 근거로 활용했다.

### 18. SSE를 사용한 이유는 무엇인가요?

채팅은 서버에서 클라이언트로 진행 상태와 토큰이 연속 전달되는 단방향 흐름이 중심이다. WebSocket보다 연결 모델이 단순하고 기존 HTTP 인증·프록시와 결합하기 쉬워 SSE를 선택했다.

### 19. 로그 때문에 업무 응답이 느려지지 않나요?

서비스별 로그를 메모리에 모아 Batch API와 Kafka로 비동기 전달한다. 업무 트랜잭션에서 매번 로그 DB를 직접 호출하지 않는다.

### 20. Kafka가 장애 나면 업무도 실패하나요?

관측 경로는 업무 실행과 분리했다. 로그 전달 실패는 재시도하거나 배치 상태로 남기되 사용자 업무 요청의 성공 여부와 분리하는 것이 원칙이다.

### 21. Retry로 중복 예약될 수 있지 않나요?

변경 요청에는 멱등 키와 payload hash를 사용한다. 동일 요청의 재시도는 저장된 결과를 반환하고 같은 키에 다른 payload가 들어오면 409로 거절한다.

### 22. 왜 409를 실패로 세지 않나요?

예약 충돌 같은 409는 시스템 장애가 아니라 정상적인 업무 규칙 거절이다. `rejected`와 `failure`를 분리해 답변 성공률과 시스템 장애율이 왜곡되지 않게 했다.

### 23. 서버 간 인증이 꼭 필요한가요?

내부 네트워크도 침해되거나 잘못된 서비스가 호출할 수 있다. 서버마다 Client Credentials와 최소 Scope를 발급하고 대상 서버가 서명·발급자·대상·Scope를 검증한다.

### 24. 사용자 토큰을 그대로 다음 서버로 넘기면 되지 않나요?

사용자 세션과 서비스 권한의 수명·책임이 다르다. 서버 전용 토큰을 사용하면 호출 주체와 허용 API를 명확히 제한하고 사용자 토큰 노출 범위를 줄일 수 있다.

### 25. 개인정보는 로그에 남지 않나요?

Tool 입력 로그에는 차량 번호 등 민감 정보 마스킹을 적용하고 Secret은 기록하지 않는다. 운영 전에는 보존 기간, 접근 권한, 삭제 정책을 조직 보안 규정에 맞게 추가해야 한다.

### 26. 테스트 73개로 충분한가요?

핵심 Tool 계약과 회귀 검증에는 유용하지만 모든 자연어 표현을 대표하지는 않는다. 개발용 문항은 지속 보강하고 최종 비교에는 별도 Holdout을 사용해 과적합을 줄였다.

### 27. LLM Judge를 믿을 수 있나요?

LLM Judge는 생성 답변의 의미 품질 보조 지표다. Tool, 인자, 호출 순서처럼 정답이 명확한 항목은 코드로 채점하고, Judge 점수만으로 모델을 선정하지 않는다.

### 28. 커버리지 73.63%면 나머지는 위험하지 않나요?

커버리지는 실행된 코드 비율이지 결함률이 아니다. 핵심 업무 경로와 오류·경계 조건을 우선 테스트했고, 미검증 영역은 리포트로 식별해 후속 테스트 대상으로 관리한다.

### 29. DB를 왜 두 개로 나눴나요?

사용자·인증·채팅·로그와 업무·RAG 데이터는 변경 주체와 보안 경계가 다르다. 서비스 책임과 장애 범위를 분리하면서 API를 통해서만 접근하도록 했다.

### 30. 실제 운영에 바로 쓸 수 있나요?

핵심 기능과 안전장치, 테스트는 구현했지만 현재 배포는 단일 Docker Compose 기반 시연 구조다. 운영 전에는 HA, 백업·복구 훈련, TLS, Secret Manager, 부하 테스트, 보안 점검, 개인정보 보존 정책이 추가되어야 한다.

### 31. LLM 서버가 중단되면 어떻게 되나요?

자연어 분석과 답변 생성은 실패하므로 사용자에게 재시도 가능한 오류를 안내한다. 업무 DB는 손상되지 않으며 승인되지 않은 변경도 실행되지 않는다. 운영 환경에서는 모델 이중화나 API 모델 폴백 정책을 검토할 수 있다.

### 32. OpenAI API가 중단되면요?

현재 음성 인식과 RAG 질의 임베딩에 영향이 있다. 텍스트 기반 일반 업무 중 RAG가 아닌 경로는 온프레미스 모델이 살아 있다면 일부 동작할 수 있다. 완전한 폐쇄망 목표라면 로컬 임베딩과 음성 모델로 교체해야 한다.

### 33. 성능 병목은 어디인가요?

하네스 결과에서 평균 Tool 지연은 약 0.29초지만 첫 답변 토큰은 약 15.47초다. 따라서 현재 주 병목은 업무 API보다 LLM 추론과 프롬프트 크기다.

### 34. 토큰을 어떻게 줄였나요?

Compact DTO, 도메인별 허용 Tool 제한, 공통 Draft Tool, 고정 UI 문구 분리, 대화 요약, 조회 목적 단위 Tool로 반복 호출을 줄였다.

### 35. 사용자가 요청을 취소하거나 수정하면 이전 결과는 어떻게 되나요?

변경 완료 후 Snapshot과 Draft 상태를 갱신해 채팅 목록과 카드에 반영한다. 완료된 빠른 실행 버튼은 다시 실행되지 않도록 비활성화한다.

## 21. 주말 학습 순서

### 토요일 저녁: 업무 시연 복기

- 회의실 예약과 충돌

- 식당 여러 장소·끼니 조회
- 사내 규정과 출처 원문 요청

각 시나리오에서 어떤 Tool, 어떤 화면, 어떤 Backend 검증이 발생하는지 말한다.

### 일요일 오전: RAG 집중

1. Hard Filter와 Soft Boost 차이를 설명한다.

4. 무응답 오류율을 왜 함께 봤는지 설명한다.
5. 위험 답변 검증과 1회 교정 흐름을 그린다.

### 일요일 오후: 모델과 테스트
